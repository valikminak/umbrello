# Общие настройки Cloudflare Worker

У приложения один существующий Worker, один приватный bucket `Umbrello`
и один список разрешённых Telegram-аккаунтов. Настройки задаются в
**Settings → Variables and Secrets**, секреты в репозиторий не записываются.

| Имя | Тип | Назначение / значение |
| --- | --- | --- |
| `BOT_TOKEN` | Secret | Существующий токен бота: проверка Telegram-подписи и отправка сообщений |
| `CHAT_ID` | Variable | Чат, куда бот отправляет отчёты и уведомления об отказе во входе |
| `ALLOWED_USER_IDS` | Variable | Числовые Telegram ID через запятую, например `111111111,222222222` |
| `SUPABASE_URL` | Variable | Существующий URL проекта `https://<project-ref>.supabase.co` |
| `SUPABASE_SERVICE_ROLE_KEY` | Secret | Существующий серверный ключ Supabase: `sb_secret_…` или legacy service-role JWT |
| `SUPABASE_BUCKET` | Variable | `Umbrello` — точное имя общего приватного bucket, с учётом регистра |
| `OPENAI_API_KEY` | Secret | Существующий ключ для запросов к ИИ |
| `OPENAI_MODEL` | Variable | Существующий ID модели |

`CHAT_ID` — адресат сообщений, `ALLOWED_USER_IDS` — пользователи с доступом.
Они могут содержать одно и то же число, но выполняют разные задачи. ID получателя
сам по себе не даёт доступ. Дополнительных bucket и ключей для Books не нужно.

## Переход с прежних имён

1. Перенеси значение `GRAMMAR_ALLOWED_USER_IDS` в `ALLOWED_USER_IDS`.
2. Перенеси значение `SUPABASE_GRAMMAR_BUCKET` в `SUPABASE_BUCKET` (`Umbrello`).
3. Если ранее добавлял `BOOKS_ALLOWED_USER_IDS`, объедини нужные ID в общий список.
   Если задавал `SUPABASE_BOOKS_BUCKET`, материалы Books должны находиться
   в общем bucket `Umbrello` по прежним путям `books/…`.
4. Опубликуй актуальный `worker/cf_worker.js` вместе с новыми переменными.
   Удали старые `GRAMMAR_ALLOWED_USER_IDS`, `BOOKS_ALLOWED_USER_IDS`,
   `SUPABASE_GRAMMAR_BUCKET`, `SUPABASE_BOOKS_BUCKET`: новый код их не читает.
5. Сохрани остальные переменные и секреты. Обновление GitHub Pages само по себе
   не обновляет Worker; его нужно отдельно опубликовать в Cloudflare.

Флаг совместимости `cache_option_enabled`, если он уже включён, оставь.
Имена файлов и каталогов в Storage не меняются из-за переименования переменной:

```text
Umbrello/                         ← bucket (не Public)
└── books/
    ├── index.json
    └── the-woman-in-the-dunes/
        └── book.json
```

## Как применяются настройки

- Каждый рабочий POST-запрос сначала проходит проверку Telegram-подписи,
  затем общего `ALLOWED_USER_IDS`: проверка входа, Books (включая definitions
  через `/books/define`, который использует настройки OpenAI), Write
  и отправка отчётов, в том числе результатов теста Grammar. Своих маршрутов
  у Grammar нет: вопросы лежат в проекте.
- Пустой или некорректный список закрывает доступ к этим API. Имя профиля
  в URL не влияет на проверку.
- Отсутствующий `SUPABASE_BUCKET` даёт ошибку конфигурации. Скрытого перехода
  к `grammar` или к отдельному bucket раздела нет.
- Перед показом профилей и уроков каждая страница запрашивает `POST /access/check`.
  Проверка включена и для прямых ссылок на разделы. Любой ответ, кроме
  подтверждённого `allowed` (отказ, ошибка конфигурации, неверная подпись,
  сбой сети, открытие вне Telegram), показывает один и тот же экран:
  бесконечную анимацию зонтика без текста, ID и кнопок. Причина остаётся
  на сервере. Запрос выполняется один раз на загрузку страницы; экран
  ничего не повторяет и не опрашивает Worker. Новая проверка — только
  закрыть и снова открыть Mini App.
- Страницы — публичные файлы GitHub Pages, поэтому входной экран можно обойти.
  Тот же зонтик поднимается на любой странице, когда Worker отвечает
  `app_forbidden`, `books_forbidden`, `*_not_configured`
  или `unauthorized` на запрос Books, Write или отправку отчёта
  (`Profiles.refuse(code)` в `assets/js/profiles.js`). Страница блокируется
  целиком; ID и текст ошибки не показываются.
- Решение о доступе не сохраняется в localStorage. Новая страница и возврат
  через кэш истории браузера требуют новой проверки. Сеть или неверный ответ
  Worker не дают доступ.
- HTML, JS и обычные учебные JSON на GitHub Pages остаются публичными файлами:
  экран входа закрывает интерфейс Mini App, но не приватизирует статический хостинг.
  Книги в закрытом Supabase защищены серверной проверкой Worker.

## Уведомления об отказе

При отказе подтверждённому Telegram-аккаунту Worker отправляет в `CHAT_ID`
сообщение существующим ботом:

```text
🔒 Попытка входа в Umbrello

Имя: Anna Example
Username: @anna_example
ID: 123456789

Доступ не выдан. Чтобы разрешить вход, добавь этот ID в ALLOWED_USER_IDS.
```

Имя, username и ID берутся только из подписанного `initData`. Неподписанные
запросы не вызывают отправку сообщений. Если username отсутствует, так и указано.
Дополнительных переменных, базы данных и настройки webhook не требуется.

Успешная отправка помечается на 24 часа в Cloudflare Cache API; одновременные
запросы одного аккаунта объединяются внутри экземпляра Worker. Это подавляет
обычные повторные открытия. Кэш локален для дата-центра и может очищаться,
поэтому строгой глобальной гарантии «одно сообщение в сутки» нет.
Подробности механизма — [Cloudflare Cache API](https://developers.cloudflare.com/workers/runtime-apis/cache/).

После ошибки Telegram (HTTP-ошибка, `ok: false`, таймаут или сбой сети) Worker
делает паузу: 5 минут без новых попыток отправки для всех аккаунтов; при ответе
429 пауза не меньше `retry_after`, но не дольше часа. Пауза хранится в памяти
экземпляра и в Cache API, так что это тоже не строгий глобальный лимит. Во время
паузы доступ остаётся закрытым, а `notificationSent` в ответе равен `false`.

Поле `notificationSent` остаётся в API, но экран его не показывает: пользователь
видит только зонтик. ID нового аккаунта владелец узнаёт из уведомления бота.
Если бот не настроен, ID на экране больше нет — его придётся узнать другим
способом (например, через любой бот, показывающий Telegram ID). В логах Worker
остаётся сообщение об ошибке отправки без токена, имени или ID пользователя.

Про нагрузку: запросы отклонённых аккаунтов всё равно расходуют квоту Worker
(проверка подписи и ответ 403). До OpenAI и Supabase они не доходят: список
доступа проверяется раньше любого маршрута. Жёсткого лимита на число запросов
нет; при необходимости его можно добавить правилами Cloudflare Rate Limiting
без изменения кода.

## Публикация

1. Опубликуй обновлённый `worker/cf_worker.js` в Cloudflare. Сохрани текущие
   `ALLOWED_USER_IDS`, `BOT_TOKEN`, `CHAT_ID` и остальные общие настройки.
2. Опубликуй изменения HTML и `assets/` на GitHub Pages. Нужны обе части:
   старый Worker не знает маршрут `/access/check`.
3. Закрой Mini App и открой заново. При старом кэше стартовой страницы обнови
   ссылку Mini App на `index.html?v=10`.
4. Чтобы выдать доступ, добавь ID в `ALLOWED_USER_IDS` через запятую и сохрани
   настройки Worker. Пользователь закрывает и снова открывает Mini App.

Логика уведомлений и паузы покрыта `node --test tests/worker.test.cjs`;
настоящие сообщения в Telegram при проверках не отправлялись.
